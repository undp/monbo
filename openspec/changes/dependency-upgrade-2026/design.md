## Context

Monbo is a monorepo with three dependency surfaces:

- **`monbo-front`** — Next.js 15.3.1, React 19.1, TypeScript 5.7, MUI 6, managed with pnpm.
- **`monbo-api`** — FastAPI 0.115.6 on Python 3.11, dependencies pinned in `requirements.txt` (pip), heavy geospatial stack (shapely / geopandas / rasterio / pyproj). Tested with pytest.
- **`scripts/update-gfw-tmf`** — earthengine-api, geemap, GDAL, `tenacity<9`.

Docker uses `python:3.11-slim` and `node:20-alpine` (Node 20 has been EOL since 2026-04-30). There is no CI, no dependency bot; the frontend has no tests, the API has pytest. This change modernizes runtimes and dependencies and adds CI plus — as a final, standalone step — a dependency bot (Dependabot) for guardrails. The plan and all version targets below were the approved input and were transcribed faithfully. **Revised 2026-09-22:** the original targets were set on 2026-07-08 and every one of them was re-validated against PyPI, the npm registry, and the Node/Python release calendars. Version numbers were refreshed, three runtime/toolchain decisions were re-opened where the ecosystem moved underneath them (Node 22 → 24 in D4, Python 3.12 → 3.13 in D3, TypeScript pinned to 6.0.3 with 7 deferred in D10), and two risks that PR 1's lockfile had already absorbed silently were promoted to explicit gates (pandas 3 in R8, the numpy 2.4 → 2.5 crossing in D3).

## Goals / Non-Goals

**Goals:**
- Migrate Python packaging to uv (pyproject + `uv.lock` + dependency-groups); keep pnpm for the frontend.
- Raise runtimes: API to Python 3.13 (unlocking rasterio 1.5 + numpy 2), frontend to Node 24 LTS.
- Bring both dependency tracks current, up to and including MUI 7.3.11, Next 16.3.6, TypeScript 6.0.3, eslint 10.11.0, i18next 26.4.2.
- Add a root `package.json` orchestrator (option A), minimal CI, and — as a final, standalone step — a dependency bot (Dependabot).
- Ship the work as 11 reviewable PRs across two independent tracks (only PR 1 is a shared prerequisite), with PR 11 as the final standalone dependency-bot change.

**Non-Goals (deferred — see "Deferred / Out-of-scope"):**
- MUI 9, TypeScript 7, Turborepo, Python 3.14, Node 26, and the `xlsx` 0.18.5 security remediation.
- Any product/feature change, API contract change, or DB change.
- Adding frontend unit tests (out of scope for this upgrade).

## Decisions

### D1 — uv for Python, pnpm retained for frontend
Migrate `monbo-api` and `scripts/update-gfw-tmf` to uv: `pyproject.toml` with production deps + a `dev` dependency-group (pytest, pytest-cov, ruff, black, mypy), a committed `uv.lock`, and `.python-version`. Remove `requirements.txt` and collapse the duplicated `fastapi` + `fastapi[standard]` entry. pytest config (`testpaths`) moves into `pyproject.toml`. Every dev-group entry carries an exact `==` pin like the production deps do — see D9; leaving ruff/black/mypy unpinned lets an unrelated `uv lock` refresh in PRs 2-5 move the linters and break CI for reasons that have nothing to do with the bump under review.
*Alternative considered:* Poetry / pip-tools — rejected; uv is faster, has a first-class lockfile and dependency-groups, and integrates cleanly with Docker via `uv sync --frozen`.

### D2 — Root orchestrator "option A" (no workspace, no Turbo)
Root `package.json` with `dev` / `test` / `lint` / `build` scripts delegating via `pnpm --dir <pkg>` and `uv run --directory <pkg>`, using `pnpm exec concurrently` for parallel dev. `concurrently` is a pinned root devDependency, so the root is a minimal pnpm project with its own committed `pnpm-lock.yaml`; the frontend and Python package lockfiles remain in their package directories. This is still not a pnpm workspace.
*Alternatives considered:* `pnpm dlx concurrently` was rejected because it downloads an unpinned tool on every clean run. A pnpm workspace (which would centralize JS dependency resolution and touch Dockerfiles/Dependabot config) and Turborepo are both premature with a single JS application. Entry condition for revisiting is documented below.

*Node 22 for the orchestrator vs. the runtime decision (D4):* the pinned `concurrently` (v10) declares `engines.node >=22`, so the root orchestrator effectively wants Node 22 from PR 1 — earlier than D4/PR 8, which raises the *runtime* baseline. There is no real contradiction: the orchestrator is a **dev-convenience tool, not a runtime**. The runtime decision (`engines` in `monbo-front`, `node:24-alpine` Docker images, the CI runtime the app is built and shipped on) stays in PR 8 as D4 states; the root orchestrator merely adopts a Node 22 floor for the dev shell that runs `pnpm dev`/`test`/`lint`/`build` from PR 1. Because pnpm's `engine-strict` is off, running the orchestrator on Node 20 emits a warning rather than failing, and each package can still be run directly on Node 20 from its own directory until PR 8. PR 8 then moves the runtime past that floor to Node 24, so the orchestrator constraint is satisfied for the rest of the change. This is documented in the root README and `docs/onboarding.md`.

### D3 — Python 3.13 + rasterio 1.5 + numpy 2 together
rasterio 1.5 requires Python >=3.12 and numpy >=2 (verified on PyPI), so the interpreter bump and rasterio bump are coupled in PR 4. **Revised 2026-09-22 — the target is Python 3.13, not 3.12.** Python 3.12 left its bugfix window in April 2025 and is security-only; 3.13 is the current bugfix line (EOL 2029-10-31). The whole geospatial stack ships cp313 wheels — verified for rasterio 1.5.1, pyproj 3.8.0, shapely 2.1.2, numpy 2.5.3 and pillow 12.3.0; geopandas is pure Python and pyogrio ships abi3 wheels — so the gate work in PR 4 is identical at 3.12 or 3.13 and there is no reason to land on the older interpreter. The uv lock generated in PR 1 already resolves numpy 2.4.6 under rasterio 1.4.3, so numpy 2 is introduced by the lockfile migration, not first by PR 4. Note that the PR 1 lock is a **dual resolution**: numpy 2.4.6 for `python_full_version < '3.12'` and numpy 2.5.1 for `>= '3.12'`. PR 4 therefore crosses numpy 2.4 → 2.5 as well as 1 → 2 — the baseline captured under numpy 1.26.4 was validated at 2.4.6 in PR 1 and has never run against the 2.5 series, so PR 4's gate is a genuine re-validation and not a formality. Before PR 1 can be accepted, the inherited pytest failures must be repaired and an automated, version-controlled numeric fixture/baseline captured from the pre-upgrade numpy 1 environment must pass under the PR 1 lock. PR 4 is a second hard gate that reruns the same comparison after Python 3.13/rasterio 1.5. mypy `python_version` moves 3.10 → 3.13 in the authoritative `monbo-api/pyproject.toml`; the duplicate root mypy block is removed or consolidated so it cannot drift. Docker base → `python:3.13-slim`.

### D4 — Node 24 LTS + Next 16 coupled
Next 16 itself only requires Node >= 20.9; the LTS baseline is the project's decision, not a Next requirement. **Revised 2026-09-22 — the target is Node 24, not Node 22.** Per the Node release schedule, v22 left active LTS on 2025-10-21 and is in maintenance until 2027-04-30, while v24 is the active LTS (maintenance from 2026-10-20, EOL 2028-04-30). Shipping Node 22 now would put the project on a maintenance-only runtime that expires roughly seven months after this change completes, for exactly the same amount of work. Nothing blocks 24: `next@16.3.6` needs `>=20.9`, `eslint@10.11.0` needs `^20.19 || ^22.13 || >=24`, `concurrently@10` needs `>=22`, and `react-dropzone@20` needs `>=22`. `next lint` is removed in Next 16, so the lint script becomes `eslint .`; `--turbo` is dropped from dev (Turbopack is the default) with `next build --webpack` as fallback. eslint 10 still requires Node 20.19 / 22.13 / 24+, so it must land on the established runtime. Docker base → `node:24-alpine`; `engines` floor → Node >=24; frontend CI `actions/setup-node` → 24. (Node 26 becomes LTS on 2026-10-28; it is deferred — see below — because it would land untested days after release.)

### D5 — MUI only to v7 now; v8 does not exist
Published MUI majors are 5, 6, 7, 9 — there is no v8. Upgrade 6 → 7 via the official codemod (`Grid2` → `Grid`, `@mui/material-nextjs/v15-appRouter` → `v16`), targeting the current head of the v7 line, **7.3.11** (`latest-v7` dist-tag as of 2026-09-22). v9 is deferred until a visual-regression harness exists (D-defer); it is now at 9.4.0 and mature, which strengthens rather than weakens the case for a harness before adopting it.

### D6 — Coupled version bumps in a single commit
React + `@types/react`(-dom) bump together; i18next 26 + react-i18next 17 bump together (react-i18next 17 peers `i18next >= 26.2`). `@types/node` is aligned to the real Node 24 runtime (NOT bumped to 26, whose `latest` is 26.6.2 and would describe an interpreter the project does not run).

### D7 — CI triggers on ready-for-review
Workflows fire on `types: [opened, synchronize, ready_for_review]` with `if: github.event.pull_request.draft == false`, so draft PRs don't burn CI minutes. Frontend job caches the pnpm store + `.next/cache`; API job runs `uv sync --frozen` + `uv run pytest` + ruff/black/mypy. The API workflow is temporarily report-only while inherited pytest, formatting, lint, and typing failures are repaired. That staging state is not the acceptance state: once the suite and static checks are green, every `continue-on-error` is removed and repository branch protection is verified to require both API and frontend jobs before merge.

### D8 — Dependency bot: Dependabot, added last
The automated dependency bot is **Dependabot** (`.github/dependabot.yml`), added as the **final, standalone PR** (PR 11) and decoupled from PR 1 — it is the lowest-priority guardrail and nothing depends on it. Policy: weekly schedule; group minors/patches to keep PR volume down; isolate each major into its own PR for review in isolation; bound the open-PR queue with `open-pull-requests-limit`; never automerge (every PR must pass CI + human review before merge). Coverage requires one `updates` entry per ecosystem/directory: `npm` (root orchestrator and `monbo-front`), `uv` (`monbo-api` and `scripts/update-gfw-tmf`), `docker` (each Dockerfile directory, with detection of `Dockerfile.dev`/`Dockerfile.prod` proven rather than assumed), and `github-actions`. PR 11 also decides whether the `ghcr.io/astral-sh/uv` `COPY --from` reference is in scope and records whether third-party Actions use full-SHA or major-tag pinning.

*Why Dependabot over Renovate:* Renovate is technically stronger for this stack (updates `pyproject.toml` + `uv.lock` together, granular grouping, a Dependency Dashboard, shared presets), but it requires installing the third-party Mend GitHub App (org-wide write access) or self-hosting. Dependabot is native to GitHub, needs zero extra infrastructure or third-party app, and its 2025-2026 improvements (multi-ecosystem / multi-directory grouping, uv support) close most of the gap for a repo this size. *Known caveat to verify at implementation time:* Dependabot has had uv bugs — `pyproject.toml`↔`uv.lock` desync (dependabot-core #12788) and running security updates via pip instead of uv (#13426); since `monbo-api` pins with `==`, confirm these are resolved or acceptable before relying on it.

### D9 — Pin the API dev-group tools, not just the production deps

`monbo-api`'s production dependencies use exact `==` pins, but the `dev` group ships `ruff`, `black`, `mypy` and `memory-profiler` unpinned. The PR 1 lock resolved mypy 2.2.0, black 26.5.1 and ruff 0.15.20 — meaning mypy 1 → 2 and black 25 → 26, two majors, were absorbed by PR 1 without appearing in any PR's stated scope. Left unpinned, every `uv lock` refresh in PRs 2-5 silently re-rolls the linters, so a dependency bump can fail CI on a formatting or typing rule that changed underneath it. Pin all four to exact versions and let PR 11's Dependabot propose their upgrades as reviewable PRs like everything else.
*Alternative considered:* leaving them floating so the team always lints against the newest rules — rejected; that is what a weekly Dependabot PR is for, and it does not conflate linter churn with dependency bumps.

### D10 — TypeScript 6.0.3 now; TypeScript 7 deferred on a hard blocker

TypeScript 7.0.2 became `latest` on 2026-07-08 (the Go-native compiler port); the v6 line ends at 6.0.3. The original plan said "TypeScript 6.0", which is still the right call, but it must now be an explicit choice rather than an accident of timing. TS 7 is **not adoptable today**: `eslint-config-next@16.3.6` depends on `typescript-eslint@^8.46.0`, and every published typescript-eslint release — including the 8.70.2 canary — declares `peerDependencies.typescript: ">=4.8.4 <6.1.0"`. Installing TS 7 breaks lint, which is a blocking CI step. PR 7 therefore pins **6.0.3**, the head of the supported range.
*Entry condition for TS 7:* typescript-eslint publishes a release whose `typescript` peer range admits 7.x, and `eslint-config-next` picks it up. Tracked in Deferred / Out-of-scope.

## Risks / Trade-offs

- **R1 — numpy 2 changes deforestation numbers (PRs 1 and 4).** → Repair pytest first; capture a deterministic, version-controlled reference from the pre-upgrade numpy 1 environment; run the automated ratio/decoded-imagery comparison under PR 1's numpy 2.4.6 lock and again under PR 4, where the same lock resolves the numpy **2.5** series on Python >= 3.12 (D3) — PR 4 is a real re-validation against an unseen numpy minor, not a repeat of PR 1's run. Block either PR unless the concrete tolerances in the Python capability spec and the full pytest suite pass on Linux x86_64 CI. This is the single most critical validation gate.
- **R2 — Next 16: Turbopack default / standalone output / MUI SSR (PR 8).** → CI covers frozen install + type-check + lint + build. Separately, PR 8 requires a documented manual verification of `output: "standalone"` via `postbuild` + `start:standalone` and MUI SSR; it is deliberately not represented as a CI step. Keep `next build --webpack` as fallback and evaluate the middleware→proxy codemod for `src/middleware.tsx`.
- **R3 — i18next 26 `TFunction` typing (PR 9).** → Land after PR 7 (TS 6) so the type toolchain is settled; fix the usages of `TFunction` (8 files, verify with grep at implementation time); exhaustive es↔en smoke of all flows.
- **R4 — MUI 7 visual regressions (PR 10).** → Run the official codemod, migrate `Grid2` → `Grid` and the App Router import path, and complete a manual visual review checklist (no automated visual regression yet — that gates MUI 9).
- **R5 — No frontend automated tests.** → CI relies on `tsc --noEmit` + lint + build + manual smoke of 4 flows in es and en; accepted for this upgrade.
- **R6 — Version drift between coupled packages.** → Enforce single-commit coupling for React/@types and i18next/react-i18next (D6); CI `--frozen` installs catch lockfile drift.
- **R7 — Peer/engine floor violations.** → eslint 10 needs Node >= 20.19/22.13/24+; `react-dropzone` 20 and `concurrently` 10 need >= 22; Next 16 itself only needs Node >= 20.9 (Node 24 LTS is the project's approved baseline, not a Next requirement). PR 8 establishes Node 24 in `engines`, Docker, CI, and `@types/node`; neither PR 7 (eslint 10) nor PR 10 (react-dropzone 20) may land until PR 8 has landed, so both are always installed and validated on the declared runtime. The TypeScript peer floor cuts the other way: `typescript-eslint` caps `typescript` at `<6.1.0`, so PR 7 pins 6.0.3 rather than tracking `latest` (D10).
- **R8 — pandas 2 → 3 entered silently through the PR 1 lock.** `geopandas` requires `pandas>=2.0.0` with no upper bound, so `monbo-api/uv.lock` resolved **pandas 3.0.3** — a major with copy-on-write and default string-dtype changes — without appearing in any PR's stated scope. The API reaches pandas only transitively through `geopandas` (`app/modules/deforestation_analysis/helpers.py`), and the PR 1 suite plus numeric gate pass, so this is recorded rather than reverted. → Add `pandas` to the `tooling` block of `tests/numeric_baseline/baseline.json` so the interpreter bump in PR 4 cannot move it unobserved, and re-check it in PR 4's gate alongside numpy.

## Migration Plan

1. **PR 1 first** (shared prerequisite): establishes uv, the root orchestrator, and CI. CI may be introduced in report-only mode solely to expose inherited failures. Before PR 1 is accepted, repair pytest/static checks, capture the approved numpy 1 fixture/baseline, pass it and the suite under the PR 1 lock (numpy 2.4.6), remove every `continue-on-error`, and verify API/frontend jobs are required by branch protection. Local/Docker *runtimes* stay on Python 3.11/Node 20 (the per-package baseline; the frontend `engines` floor and `node:24-alpine` images move to Node 24 in PR 8). The one exception is the root orchestrator dev tool: its pinned `concurrently` wants Node ≥22 (see D2), so running `pnpm dev`/`test`/`lint`/`build` from the repo root expects Node 22 — running each service directly stays fine on Node 20. Frontend CI already uses Node 22 and `packageManager` is set. Nothing else merges before PR 1.
2. **Run the two tracks in parallel** after PR 1:
   - Python track: PR 2 → 3 → 4 → 5 (PR 4 repeats the runtime/numeric gate first enforced in PR 1).
   - Front track: PR 6 → PR 8 → PR 7 → PR 9 → PR 10. PR 8 establishes Node 24 before eslint 10 in PR 7 and before react-dropzone 20 in PR 10; PR 9 requires PR 7.
   - Dependency bot: PR 11 (Dependabot) lands **last**, after both tracks — it is standalone and depends on nothing, so it is sequenced last as the lowest-priority guardrail.
3. **Per-PR validation** (see below) must pass in CI before merge; risky PRs (4, 8, 9, 10) additionally require the documented manual smoke.
4. **Rollback**: each PR is independently revertible. Because runtime bumps (PR 4 Python 3.13, PR 8 Node 24) are isolated in their own PRs, a runtime regression can be rolled back without reverting the dependency-currency PRs. CI (PR 1) and Dependabot (PR 11) are additive and safe to keep.

### Validation
- **API:** blocking CI runs `uv sync --frozen` + `uv run pytest` + ruff/black/mypy. The pytest suite includes the deterministic numpy baseline comparison; smoke `/health` + a deforestation analysis. The numeric gate runs before accepting PR 1 and again in PR 4.
- **Front:** CI runs `install --frozen-lockfile` + `tsc --noEmit` + lint + build. PR 8 separately records a manual `postbuild` + `start:standalone`/MUI SSR result. Manual smoke covers 4 flows in **es and en**: (1) home / country selection, (2) polygon validation with upload + Excel/GeoJSON downloads, (3) deforestation analysis with map/clusters/modals, (4) PDF report.

## Deferred / Out-of-scope (with entry conditions)

- **MUI 9** — deferred until a visual-regression harness exists. Entry condition: automated visual regression in place; then handle `PaperProps` → `slotProps` and the focus/click behavior changes in `ButtonBase` / `Menu` / `Tabs`.
- **Turborepo** — deferred. Entry condition: a *second* JS package appears → first introduce `pnpm-workspace` (centralizes JS package resolution; the existing minimal root orchestrator lockfile would be regenerated as the workspace lock and Dockerfiles + Dependabot config would change), and adopt Turbo only if build orchestration actually hurts.
- **TypeScript 7** — deferred on a hard blocker, not a preference (D10). `typescript@7.0.2` is `latest`, but every published `typescript-eslint` release caps the peer at `typescript <6.1.0`, and `eslint-config-next` depends on it, so TS 7 breaks the blocking lint step. Entry condition: typescript-eslint ships a release admitting 7.x and `eslint-config-next` adopts it; then re-run PR 7's `tsc --noEmit` + lint + build against 7.x.
- **Python 3.14 / Node 26** — deferred; this cycle lands on the current active baselines, Python 3.13 and Node 24 (revised 2026-09-22; the original 3.12 / 22 targets are superseded by D3 and D4). Python 3.14 is already viable on the dependency side — rasterio, pyproj, shapely, numpy and pillow all publish cp314 wheels — so the entry condition is appetite, not availability. Node 26 becomes LTS on 2026-10-28; entry condition is one release cycle of soak time after that date.
- **`xlsx` 0.18.5** — separate security debt; evaluate the official SheetJS distribution or consolidating on `exceljs`. Tracked independently of this upgrade. Re-checked 2026-09-22: the npm registry still serves 0.18.5 as `latest`, so the debt is unchanged and no upgrade path exists on npm — remediation still means changing distribution channel or library.
